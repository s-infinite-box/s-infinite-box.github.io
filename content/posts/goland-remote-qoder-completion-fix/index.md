在 GoLand 远程开发中遇到一个很绕的问题：Qoder 已安装、前后端插件页都显示启用，远端日志也能看到补全结果，编辑器里却没有提示。换成独立 JetBrains Client 后，提示终于出现了，但按 Tab 只会缩进，Ctrl+Q 也不稳定，只有鼠标点击“接受”始终有效。

最终跑通的组合是：**使用与后端匹配的独立 JetBrains Client，只在前端启用 Qoder，停用后端 Qoder。** 补全、Tab、Ctrl+Q 和侧边聊天都恢复正常。后端插件没有卸载，安装文件和备份保留下来，便于回退。

这是一次具体版本组合的排查记录。下面把两个不同故障、失败实验和验证过程分开讲清楚，方便遇到相似现象时逐层判断。

## 环境与现象

排查发生在 2026 年 10 月 15 日，环境如下：

| 组件 | 本次版本或运行方式 |
| --- | --- |
| 本地系统 | macOS，Apple Silicon |
| 远端系统 | Linux |
| IDE | GoLand 2026.2.3，Build 262.10968.67 |
| 独立客户端 | JetBrains Client，Build 262.10968.67 |
| QoderCN 插件 | 2026.1014.79711813 |
| Qoder 核心 | 2026.1014.79696485 |

这里的“前端”是 Mac 上负责显示窗口、编辑器和处理本地交互的客户端；“后端”是 Linux 上打开项目、提供语言分析等能力的 IDE 进程。

先做了一次本地模式对照：直接启动本地完整 GoLand，不连接远端，安装 Qoder 后补全正常。这说明同一台 Mac 上，Qoder 至少能够在本地模式生成并显示建议。故障范围因此收缩到了远程开发的运行方式。

但这仍不能证明远程前端正常。完整 GoLand 的本地配置，与远程客户端使用的插件目录、配置目录和运行模块，都需要分别检查。

## 第一层：插件启用了，却没有实际加载

最开始，远程连接由完整的 `GoLand.app` 以 `thinClient` 模式启动前端。插件页显示 Qoder 已启用，很容易让人把注意力转到网络、登录和补全服务。

客户端启动日志给出了不同答案：Qoder 根本没有完成加载。

当时的依赖链可以简化为：

```text
前端缺少 VCS 后端模块
    ↓
Git 后端模块被排除
    ↓
依赖它的 Qoder 被整体排除
```

这里最容易误判的是：**Git 插件本身仍然显示已加载。** 一个插件包可以包含多个模块，包级别可用，不代表其中每个后端模块都能在前端运行。

继续检查 Qoder 的插件描述文件，Git 原本被声明为可选依赖。但本次平台加载器还会根据旧式依赖声明，为插件补入 Git 的后端与共享模块依赖。这些隐式依赖参与了加载判定，最终把 Qoder 一起排除了。

这段机制能够在 JetBrains 的 [`ProductPluginInitContext.kt`](https://github.com/JetBrains/intellij-community/blob/idea/262.10968.63/platform/core-impl/src/com/intellij/ide/plugins/ProductPluginInitContext.kt#L280-L284) 中找到对应逻辑。链接是相邻的 `262.10968.63` 标签；本次还对照了实际运行的 `262.10968.67` 字节码，相关逻辑一致。它解释的是平台兼容处理，并不是 Qoder 自己的源码。

因此，“已安装”“已启用”“实际已加载”要分别确认：

| 状态 | 能说明什么 |
| --- | --- |
| 已安装 | 对应配置目录中有插件文件 |
| 已启用 | 配置允许 IDE 尝试加载它 |
| 实际已加载 | 当前进程通过依赖检查，并开始执行插件代码 |

只有第三项才能支持后面的功能判断。

### 为什么独立客户端有用

接下来换成官方独立 JetBrains Client，并保持与后端相同的 Build。

对比这两个安装包，本次独立客户端包含 Git 的前端模块，没有完整 IDE 包中的 Git 后端描述。因此，它避开了前面那条加载阻塞，Qoder 在前端实际启动，编辑器里的建议也随之恢复。

这不是“同一个图标换种打开方法”那么简单。即使产品版本相同，完整 IDE 与独立客户端所带的模块也可能不同。JetBrains 的[模块化插件说明](https://plugins.jetbrains.com/docs/intellij/modular-plugins.html)也强调了前端、后端环境与模块依赖的区别。

换完客户端之后，还要检查实际进程路径和本次启动日志，确认启动的是目标客户端。连接成功或窗口标题相同，都不能替代这一步。

## 第二层：提示回来了，键盘却采纳不到

更换客户端解决了“不显示”，但并没有解决所有问题。

当时前后端都启用了 Qoder，表现是：

- 鼠标点击建议旁的“接受”，可以稳定写入代码。
- Tab 只产生缩进，空白行和已有代码后都无法正常采纳。
- Ctrl+Q 有时有效，有时也无法采纳。

最初怀疑快捷键冲突。检查后发现 Tab 与 Ctrl+Q 已绑定同一个采纳动作，因此没有继续改键位。既然鼠标可以稳定采纳，补全内容和写入能力应当已经具备，下一步要比较的是鼠标和键盘实际走了哪条调用路径。

对照同一轮操作的前后端日志后，发现两边各自产生了一份建议，而且请求标识不同。为了说明关系，用 A、B 代替真实请求标识：

```text
前端：请求 A → 显示建议 A → 鼠标接受 A
后端：请求 B → 保存建议 B → 键盘动作尝试接受 B
```

用户看见的是前端建议，键盘动作却被送到了后端。即使两份建议碰巧内容相似，它们也不是同一个待采纳状态；这也解释了为什么 Ctrl+Q 偶尔成功，鼠标却始终正常。

本次对平台类的反编译检查进一步确认：`FrontendActionsRegistrationHost.registerAction` 会处理两端注册的同名动作，前端动作被 `BackendDelegatingAction` 替换，转交后端执行。当前 Qoder 动作没有使用让它保留在前端执行的 `FrontendOnly` 标记。

到这里，问题已经超出了“Tab 有没有绑定正确”：显示建议的一端，与键盘执行采纳的一端错位了。

## 用两次单端实验定位

知道两端都在运行，并不能直接决定应该保留哪一端。这里做了两次可回滚实验，每次只改变一个端的启用状态。停用前端后重开前端；停用后端时正常保存项目并重开后端，再连接客户端，让新状态真正生效。

| 前端 Qoder | 后端 Qoder | 实际结果 |
| --- | --- | --- |
| 启用 | 启用 | 有建议；鼠标正常，键盘采纳异常 |
| 停用 | 启用 | 编辑器没有建议；实验失败并恢复 |
| 启用 | 停用 | 补全、Tab、Ctrl+Q、侧边聊天均正常 |

第一轮只保留后端。后端日志仍有请求和 `shown` 记录，但编辑器里没有提示。这说明 **日志里的“shown”不等于远程用户实际看见了建议**。这个方案不符合使用要求，所以恢复前端配置，继续做另一组实验。

第二轮保留前端，停用后端。这次用户实际验证了四项功能：显示补全、Tab 采纳、Ctrl+Q 采纳、侧边聊天，结果均正常。

日志也有对应变化：前端中显示、应用和接受对应同一个请求标识；后端重新启动后的日志不再出现 Qoder 的运行记录。用户看到的建议与键盘采纳终于属于同一份状态。

后端采用停用而非卸载，安装文件和备份保留。这样验证不通过时，可以恢复启用状态，不必重新安装和登录。

## 修复步骤与验证

如果遇到相近现象，可以参考下面的顺序，但应以自己的日志和版本为准：

1. 在本地完整 IDE 中做一次功能对照，确认问题是否只出现在远程模式。
2. 记录前端、后端、插件的完整版本与实际进程路径。
3. 分别检查两端启动日志，确认插件实际加载，尤其留意依赖缺失和模块被排除。
4. 如果命中本次完整 IDE 前端的加载问题，换用与后端匹配的官方独立客户端，再核对进程路径和加载结果。
5. 当建议可见而键盘采纳失败时，比较鼠标和键盘操作对应的请求标识及执行端。
6. 备份后做单端启用实验，正常保存并重开对应端，再重连验证；失败时恢复上一状态。

查看日志时，可以先从 IDE 的“帮助”菜单定位当前日志目录，避免误读旧会话。下面的示例假定已把两端本次日志复制到同一台分析机器，再把两个本地文件的路径赋给变量：

```bash
# 使用本次前端启动日志的实际路径
FRONT_LOG='/path/to/frontend/idea.log'

# 使用已复制到分析机器的后端启动日志路径
BACK_LOG='/path/to/backend/idea.log'

rg -n -i 'qoder|excluded|cannot load|dependency' "$FRONT_LOG"
rg -n -i 'code-nes-(shown|accept)|do apply inline completion' "$FRONT_LOG" "$BACK_LOG"
```

不同版本的日志字段可能变化。关键是找到同一轮操作的请求、显示与采纳记录，并按请求标识对齐，不能把不同时间的成功日志拼在一起当作证据。分享日志前也要去掉账户、连接信息、令牌和项目内容。

最后的验收应在远程文件中实际操作：空白行触发建议，已有代码后再次触发，分别测试 Tab、备用快捷键、鼠标接受，以及侧边聊天；重连后再确认配置和启动入口仍然正确。

本次验证的是前面列出的版本与环境。后续 Qoder 或 JetBrains 平台可能调整拆分模式的实现，因此“只在前端启用”应作为这个组合已验证的处理方法。升级后如果行为变化，应重新检查加载与动作路由。

另外，本次使用的是独立客户端的直接启动入口，尚未把 Toolbox 的后续选择固定到这个客户端。以后重新连接时，仍需确认启动的确实是独立 JetBrains Client。

## 这次排查留下的方法

这次故障分成了两层：第一层是插件没有加载，第二层是插件加载后，两端的补全状态与键盘动作发生错位。把它们混在一起，就容易反复安装插件、重绑快捷键，却始终绕不开真正的阻塞。

更有效的顺序是沿着实际链路逐段核实：**文件存在 → 配置启用 → 进程加载 → 请求返回 → 编辑器显示 → 采纳写入。** 每一步只证明自己所在的那一层，下一层还需要新的证据。

远程开发尤其需要同时看前后端。两个进程都能正常工作，并不意味着它们组合起来就一定正确；鼠标和键盘看似完成同一个操作，也可能执行了不同的路径。把请求标识和用户看到的结果对应起来，再用单变量实验验证，才能让修复结论站得住。
